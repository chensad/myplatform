# MYIR i.MX8M Plus + Jetson Orin Nano Super 双脑机器人项目总路线

这份文档只做一件事：把项目从现在到可演示、可面试、可继续扩展的整体路线固定下来。

适用范围：

- 下位机：`MYIR i.MX8M Plus`
- 上位机：`Jetson Orin Nano Super`
- 项目定位：先做“底层扎实、链路可靠、安全可解释”的工程型作品，再补视觉/导航增强项

本文不展开到文件级实现细节，只定义路线、阶段目标、里程碑、验收口径和近期优先级。

---

## 1. 项目目标

项目最终要形成的，不是一个“能动起来”的 demo，而是一套可以完整讲清楚的双脑机器人基座：

- Jetson 负责 ROS2、感知、速度规划、可视化、录包与上层调试
- i.MX8MP Linux 负责 BSP、驱动、板级外设、日志、配置、下位机网关
- i.MX8MP 的 M7 负责安全状态机、断链降级、急停/撞条锁存、运动授权裁决

最终你要能讲清楚 5 个问题：

1. 为什么要双脑，而不是单板全做
2. 为什么安全逻辑要下沉到 M7，而不是全放 Linux/ROS2
3. 为什么控制链路不能裸发 `/cmd_vel`
4. 为什么这个系统是“可测、可复现、可诊断”的
5. 如果继续做成产品，现有架构怎么演进

---

## 2. 总体路线

项目按 4 层目标推进，不建议跳步。

### 第 1 层：先把下位机地基打稳

目标：

- Yocto 能稳定构建
- 板子能稳定启动
- 串口、网口、基础外设可验证
- 文档和日志留痕

这是整个项目的地基。没有这一层，后面所有 ROS2、感知、安全都不稳。

### 第 2 层：把异构多核和安全链打通

目标：

- M7 固件能被 Linux `remoteproc` 拉起
- Linux 与 M7 能通过 `rpmsg` 交换最小安全状态
- 急停/撞条/断链至少能形成一条真实安全降级链

这是项目最有“底层深度”的部分，也是和普通 ROS2 项目拉开差距的关键。

### 第 3 层：把双板通信和控制闭环打通

目标：

- Jetson 和 i.MX8MP 通过以太网稳定通信
- Jetson 发控制租约，下位机执行并回传状态
- 断链必停、故障可见

这一层完成后，项目就已经具备“系统工程”骨架了。

### 第 4 层：再补感知、安全策略、量化指标和交付物

目标：

- ROS2 bridge、感知安全节点、录包复现
- 指标统计、故障注入、长稳测试
- 形成演示视频、技术文档、面试话术和交付物清单

这一层决定项目是“会跑”，还是“像工程作品”。

## 3. 分阶段路线图

下面按推荐顺序定义阶段。

### 阶段 A：环境与构建基线

目标：

- 固定 `myplatform` 为 i.MX8MP 的统一入口
- 固定 `Ubuntu 18.04 Docker` 为 Yocto 构建环境
- 固定板级输出目录、镜像路径、刷机方式、串口登录方式

要完成的事：

- 跑通 `make BOARD=myir_imx8m_plus vars`
- 跑通 `make BOARD=myir_imx8m_plus yocto`
- 找到最终镜像产物目录
- 刷写镜像并确认板子启动到 shell
- 记录一次完整 bring-up 过程

阶段输出：

- 一份可复现的构建步骤
- 一份刷机步骤
- 一份串口启动日志

验收标准：

- 新开一次容器后，仍能重新构建出可启动镜像
- 板子能稳定登录

### 阶段 B：板级外设与设备树

目标：

- 明确你真的掌握板级硬件描述，而不是只会跑镜像

优先顺序：

1. GPIO：急停输入、撞条输入、状态输出
2. CAN：底盘或台架通信
3. I2C：IMU 可作为加分项

要完成的事：

- 确认当前使用的 dtb
- 通过 Yocto 补丁方式修改 DTS
- 打通至少 2 项基础外设
- 记录 pinmux、节点、验证命令

阶段输出：

- 一份板级引脚/外设映射表
- 至少 2 项外设的验证记录

验收标准：

- 能说清楚“哪个设备树节点对应哪个物理接口”
- 能用命令验证外设真的工作

### 阶段 C：M7 bring-up 与 remoteproc

目标：

- Linux 侧能稳定加载、启动、停止 M7 固件

要完成的事：

- 找到 `remoteproc` 的 sysfs 路径
- 先用示例 M7 固件验证路径
- 跑通 firmware 指定、启动、停止、状态查看
- 记录常见错误，比如段地址或加载失败

阶段输出：

- 一套固定的 M7 启停命令
- 一份 remoteproc 调试笔记

验收标准：

- `state` 能切到 `running`
- `dmesg` 中有明确的 remoteproc 启动痕迹

### 阶段 D：rpmsg 最小闭环

目标：

- Linux 和 M7 之间能交换最小安全消息

第一版不追求复杂：

- 只要有 `heartbeat + flags + fault_code + timestamp` 就够

要完成的事：

- 确认 rpmsg channel 名称
- 跑通最小 ping/pong 或 heartbeat
- 定义统一的 `rb_state`
- 明确未来用户态读取接口形态

阶段输出：

- 一份最小状态结构定义
- 一份 rpmsg 联调记录

验收标准：

- Linux 侧能稳定收到 M7 心跳
- 心跳中断时能被 Linux 侧检测

### 阶段 E：安全岛最小实现

目标：

- M7 不只是“能通信”，而是开始承担安全职责

第一版只做 4 件事：

- 急停采样
- 撞条采样
- 心跳上报
- 超时锁存 / 断链降级

建议状态机：

- `BOOT`
- `SAFE_STANDBY`
- `ARMED`
- `RUNNING`
- `SAFE_STOP`
- `FAULT_LATCHED`

阶段输出：

- 一份安全状态机定义
- 一份故障位定义

验收标准：

- 停止 Linux 心跳后，M7 进入安全状态
- 急停/撞条触发后不能静默恢复

### 阶段 F：Jetson 接入与双板协议

目标：

- Jetson 与 i.MX8MP 形成最小可控链路

协议原则：

- 不能裸发 `/cmd_vel`
- 必须带 `seq`
- 必须带 `lease_expiry`
- 必须带 `crc`
- 必须能区分 `hello / heartbeat / control / state / fault`

要完成的事：

- Jetson 装好 `JetPack 6.2.2 + ROS2 Humble`
- 确认双板以太网直连
- 写一个最小 bridge 程序
- 完成控制下发和状态回传
- 验证断链必停

阶段输出：

- 一份最小协议文档
- 一组控制/状态交互日志

验收标准：

- Jetson 可以稳定发控制
- i.MX8MP 可以稳定回状态
- 拔网线后系统进入 `SAFE_STOP`

### 阶段 G：底盘执行闭环

目标：

- 让控制链从“发消息”升级到“真的驱动执行器”

建议顺序：

1. 台架电机
2. 简化底盘
3. 再考虑正式底盘

不要一开始就把主要精力放在机械结构和整车布线。

要完成的事：

- 选定执行器接口：CAN / UART / 驱动器串口
- 先跑最小速度控制
- 形成基础状态反馈

阶段输出：

- 一套最小控制演示
- 一份底盘接口说明

验收标准：

- 下位机收到命令后能稳定输出
- 停止控制或断链时能停车

### 阶段 H：感知安全与 ROS2 系统集成

目标：

- 把 Jetson 的感知结果接到安全控制链上

建议第一版只做简单规则：

- 最近障碍距离 `< Dstop` 就停
- 距离 `< Dslow` 就限速

先用简单规则，不要一开始上复杂视觉策略。

要完成的事：

- 接入 2D 雷达或已有简单传感器
- 写 ROS2 bridge
- 写安全裁剪节点
- 形成 `/cmd_vel -> safe_cmd_vel -> 下位机` 链路

阶段输出：

- 一份 ROS2 节点关系图
- 一次障碍触发停车的演示

验收标准：

- 障碍出现时系统限速或停车
- 恢复逻辑可解释，不抖动

### 阶段 I：工程化与交付

目标：

- 把项目从“联调状态”变成“可展示、可诊断、可复现”

要完成的事：

- 做 `smoke test`
- 做 `fault inject`
- 做 `soak test`
- 做日志与诊断打包
- 记录关键指标
- 整理 demo 流程

阶段输出：

- 构建文档
- bring-up 文档
- 协议文档
- 指标文档
- 演示视频

验收标准：

- 至少一组可量化数据
- 至少一套可复现故障注入流程
- 别人能照着文档复现核心链路

## 4. 近期优先级

如果按“当前最该干什么”排序，建议严格按下面顺序推进。

### 第一优先级

- 跑通 i.MX8MP Yocto 构建、刷机、启动
- 记录 bring-up 过程

这是当前唯一必须先完成的事。

### 第二优先级

- 设备树 + GPIO/CAN 两项基础外设

这是进入 M7 和执行链前必须完成的板级基础。

### 第三优先级

- remoteproc 拉起 M7

没有这一步，后面的安全岛都是空谈。

### 第四优先级

- rpmsg 心跳与最小状态结构

这是 Linux 和 M7 真正形成系统关系的开始。

### 第五优先级

- Jetson 最小协议链路

这一步在前面都稳定后再做，效率最高。

## 5. 里程碑定义

建议只设 4 个大里程碑，不要把节奏切得太碎。

### M1：下位机基线成立

达成条件：

- Yocto 可构建
- 板子可启动
- 串口/网口正常

### M2：安全链打通

达成条件：

- M7 可被拉起
- rpmsg 心跳通
- 至少一条安全降级链成立

### M3：双板控制成立

达成条件：

- Jetson 可发控制
- i.MX 可回状态
- 断链必停

### M4：项目可展示

达成条件：

- 基础执行闭环成立
- 有至少一个感知安全场景
- 有指标、日志、文档、演示视频

---

## 6. 风险控制原则

为了防止项目失控，后面推进时遵守这 6 条。

1. 先台架，后整车
   不要让机械和布线问题把底层软件节奏打乱。

2. 先链路，后功能
   先确保构建、通信、安全链成立，再追功能丰富。

3. 先最小状态，后复杂协议
   第一版协议只做最小必需字段。

4. 先简单感知规则，后复杂 AI
   面试里可解释性比“花哨但不稳”更重要。

5. 先可测指标，后性能优化
   没有指标时，优化没有意义。

6. 不在 vendor 树里堆长期项目逻辑
   长期可维护内容应该收口到你自己的平台层。

## 7. 当前阶段结论

结合你现在的目标，“项目总路线”的建议非常明确：

- 主线继续用 `MYIR i.MX8M Plus + Jetson Orin Nano Super`
- 近期不要并行扩展到 `i.MX93`
- 近期不要把重点放在 SLAM、导航或复杂 AI
- 当前只专注 3 件事：
  - 下位机构建与启动
  - 板级外设与设备树
  - M7 bring-up 与 rpmsg

只要这三件事打稳，后面双板协议、ROS2 bridge、感知安全都是顺势往上接。
